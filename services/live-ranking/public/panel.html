아직 참가하지 않았습니다

점수는 HTTP로 직접 반영되지 않고, ingest(producer) → Kafka → aggregator(consumer)를 거쳐 Redis에 반영됩니다. 버튼을 누른 직후와 랭킹이 실제로 바뀌는 시점 사이에 약간의 지연이 있는 걸 확인하세요.

이벤트 시뮬레이션

여러 명이 동시에 점수를 올리는 상황을 8명의 봇으로 재현합니다.

멱등성 확인

같은 eventId로 이벤트를 두 번 보내도 점수가 한 번만 반영되는지 직접 확인합니다 (Kafka 재배달 시 중복 반영을 막는 멱등성 저장소 검증).

DLQ (실패한 이벤트)

재시도(3회)까지 다 실패한 이벤트는 DLQ로 이동합니다. 아무도 안 보면 조용히 사라지는 것처럼 보이던 걸, 여기서 직접 눈으로 확인합니다.

테스트 방법

  1. 지연 확인 — "참가하기" 후 "+10점 올리기"를 누르면 즉시 이벤트 로그에 "발행함"이 찍히지만, 전체 랭킹에 실제로 반영되는 건 Kafka consumer가 이벤트를 소비한 다음입니다(보통 1초 안쪽). 이 발행-반영 사이의 시간차가 이 실험의 핵심입니다.
  2. 이벤트 시뮬레이션 — "한번에 발사"를 누르면 8명의 봇에게 무작위 점수 이벤트가 쏟아지고, 랭킹이 실시간으로 뒤바뀌는 걸 볼 수 있습니다.
  3. 멱등성 확인 — "같은 이벤트 두 번 보내기"를 누르면 같은 eventId로 이벤트를 두 번 발행합니다. 점수가 두 번 반영되지 않고 한 번만 반영되는 걸 결과 문구와 이벤트 로그로 바로 확인할 수 있습니다(Redis 기반 멱등성 저장소).
  4. DLQ 확인 — "실패 이벤트 발생시키기"를 누르면 항상 실패하는 이벤트를 발행합니다. 재시도 3회가 다 소진되면(몇 초 걸림) DLQ로 이동하는데, 그 내용이 DLQ 목록에 그대로 나타나는 걸 확인하세요. 이 목록이 없으면 실패한 이벤트는 아무도 모르게 조용히 사라집니다.
  5. 초기화 — 테스트를 반복하고 싶으면 "초기화" 버튼으로 랭킹을 전부 지우고 처음부터 다시 시작할 수 있습니다.
  6. 관측 지표 — aggregator의 /metrics에서 반영 건수(live_ranking_score_events_applied_total), 중복 차단 건수(kafka_forge_deduped_total), consumer lag(kafka_forge_consumer_lag)을 함께 확인할 수 있습니다.
