주문하기

주문 저장과 outbox 기록은 하나의 DB 트랜잭션으로 같이 커밋됩니다. 그 뒤 "발행됨"으로 바뀌는 건 outbox 폴러가 몇 초마다 Kafka로 발행한 다음이고, "확인됨"으로 바뀌는 건 별도 프로세스(fulfillment)가 그 이벤트를 소비한 다음입니다 — 두 단계 지연을 순서대로 확인해보세요.

주문 목록

죽은 outbox 레코드 (dead-lettered)

발행이 계속 실패하는 레코드는 5번 재시도 후 격리돼서 더 이상 재시도되지 않습니다(재시도 무한 반복으로 다른 정상 레코드를 막지 않게). "발행 실패 유발"을 누르면 일부러 유효하지 않은 토픽으로 주문 하나를 만들어서 이 흐름을 직접 확인할 수 있습니다 — 몇 초 뒤 이 목록에 나타납니다.

이벤트 로그

아직 이벤트가 없습니다

테스트 방법

  1. 3단계 지연 확인 — "주문 생성"을 누르면 목록에 생성됨으로 바로 나타납니다. 몇 초 뒤 outbox 폴러(기본 5초 주기)가 발행하면 발행됨으로 바뀌고, fulfillment 컨슈머가 반영하면 확인됨으로 바뀝니다. "발행됨"은 발행-소비가 폴링 주기보다 빠르게 끝나면 목록 배지로는 못 보고 지나칠 수 있는데, 이벤트 로그는 서버가 내려주는 실제 시각으로 재구성해서 두 전이 모두 놓치지 않고 보여줍니다.
  2. 원자성 확인 — 주문 저장과 outbox 기록이 같은 트랜잭션이라, "생성됨" 상태로 목록에 뜬 주문은 반드시 언젠가 발행됩니다(둘 중 하나만 성공하는 경우가 없음).
  3. 발행 실패 격리 확인 — "발행 실패 유발"을 누르면 일부러 실패하는 주문을 하나 만듭니다. 재시도 5번(약 20~25초) 동안은 계속 시도되다가, 그 이후엔 "죽은 레코드" 목록으로 격리돼서 더 이상 재시도되지 않습니다 — 그 사이에 다른 정상 주문을 생성해보면, 죽은 레코드 하나가 나머지 주문의 발행을 막지 않는다는 것도 확인할 수 있습니다.
  4. 죽은 레코드 복구 — 죽은 레코드 목록에서 "복구"를 누르면 서버가 원인(이 데모에서는 유효하지 않은 토픽)을 정상으로 고친 뒤 재시도 대상으로 되돌립니다. 몇 초 뒤 주문 목록에서 실제로 "발행됨" → "확인됨"으로 이어지는 걸 확인할 수 있습니다 — 관측만 되고 되살릴 방법이 없던 걸 실제로 대응까지 할 수 있게 한 부분입니다.
  5. 관측 지표 — api의 /metrics에서 생성 건수(order_outbox_orders_created_total), 발행 지표(kafka_forge_produced_total)를 확인할 수 있습니다. fulfillment의 :3201/metrics에서는 소비 지표(kafka_forge_consumed_total)를 볼 수 있습니다.
