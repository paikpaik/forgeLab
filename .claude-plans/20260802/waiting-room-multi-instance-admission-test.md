## 플랜 실행 이력

### 완료: 2026-08-02

**결과**: 성공(백로그 검증 작업). waiting-room의 `AdmissionService`(`@Interval` 폴링
스케줄러)를 실제로 2인스턴스로 스케일해서, "단일 인스턴스 전제" 스코프 아웃 주석이 실제로
어떤 형태의 문제로 나타나는지 실측했다.

**실제 변경 파일**: 없음(임시로 `docker-compose.yml`의 `app` 포트 매핑을 `3000-3001:3000`
범위로 바꿔 스케일 테스트 후 원래(`${HOST_PORT:-3000}:3000`)로 복구 — 순수 검증용 임시
변경, 최종 diff 없음). `services/waiting-room/ARCHITECTURE.md`에 실측 결과를 "후속
(2026-08-02)" 섹션으로 기록.

**재현 방법**: 큐 초기화 → 15명 등록(배치 크기 10보다 많게) → `docker compose up -d
--scale app=2`로 2인스턴스 기동 → 5초 admission 주기 동안 두 인스턴스 로그/각자
`/metrics` 비교.

**핵심 발견**:
1. **실제 admission 결과(누가 들어가는지)는 정확함** — `zrangeWithScores`(조회 전용) +
   성공분만 `zrem`(커밋)이라는 기존 크래시 안전 설계 덕분에, 두 인스턴스가 같은 배치를
   동시에 집어도 중복 admission이나 유실 없이 정확히 15명이 admitted됨
2. **집계 지표는 부풀려짐** — 각 인스턴스가 `waiting_room_admissions_total`을 독립적으로
   증가시켜서, 두 인스턴스 값을 합산(Prometheus 멀티 타겟 표준 관행)하면 25로 잡힘
   (실제는 15)
3. **실시간 로그는 인스턴스-로컬이라 누락될 수 있음** — `AdminEventBus`가 프로세스 내부
   rxjs Subject라 인스턴스 간 공유가 안 되고, 앞에 로드밸런서도 없어서 사용자가 한
   인스턴스의 `/admin/logs/stream`만 보고 있으면 다른 인스턴스가 처리한 admission은
   그 화면에 아예 안 나타남

**계획과의 차이**: 없음 — 이번 백로그 항목은 애초에 "검증"이 목표였고 "고침"은 스코프
밖이었음(이 서비스는 설계 단계부터 단일 인스턴스 전제).

**잔존 작업**: 분산 카운터 합산(각 인스턴스 로컬 대신 Redis 공유 카운터로) 또는 공유 이벤트
버스(Redis Pub/Sub 등)로 이 문제를 실제로 고치는 건 이번 라운드 스코프 밖 — 필요해지면
별도 플랜으로 진행. 지금은 "단일 인스턴스 전제"라는 기존 설계 결정이 실제로 유효하고, 그
전제를 깰 경우 무엇이 새는지 문서로 남기는 것까지가 이번 작업의 목표였음.
